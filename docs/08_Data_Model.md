# Data Model (Client-Side Session State) — Feynman's Mirror

**Project:** Feynman's Mirror (Working Title)
**Context:** HackED 2026 — UAlberta, Solo, 48-hour hackathon
**Date:** 2026-02-16 (Updated 2026-02-19: TuteeState simplified to 4 states; Updated 2026-02-20: Client-side state architecture)

---

## Why No Database — and No Server-Side Session Store

Per NFR-05, the MVP operates as a **single-session tool** with no user accounts, no saved history, and no persistent state between sessions.

**The client (React Context) is the single source of truth.** There is no server-side `Map`, no database, no in-memory store. Each API call receives the relevant state slice from the client. The backend is fully stateless, which makes it resilient to Vercel serverless cold starts and function instance rotation.

**Implication:** No PostgreSQL, no MongoDB, no SQLite, no server-side Map. All state lives in `React.Context` in the browser. Refreshing the browser loses the session (accepted trade-off for hackathon scope).

**V2 consideration:** Persist client state to `sessionStorage` for refresh resilience. For multi-session history and user accounts, migrate to a lightweight database (SQLite via Prisma, or Supabase for hosted PostgreSQL).

## Complete Type Definitions

```typescript
// ============================================================
// APP STATE — Top-level client-side container (React Context)
// ============================================================

interface AppState {
  currentScreen: ScreenName;            // Current screen the user is on
  createdAt: Date;                      // Timestamp of session start

  // Source data (populated in S1)
  source: SourceData;

  // Oracle outputs (populated in S2, from /api/process-source response)
  // NOTE: testQuestions + answerKey are stored client-side and sent to /api/grade
  oracle: OracleData | null;

  // Conversation state (populated during S3, managed client-side)
  conversation: ConversationData;

  // Grading results (populated in S4/S5, from /api/grade response)
  grading: GradingData | null;
}

type ScreenName = 'upload' | 'topic' | 'teaching' | 'testing' | 'report';

// ============================================================
// SOURCE DATA — User's uploaded material
// ============================================================

interface SourceData {
  sourceText: string;                   // Extracted text from PDF or pasted text
  sourceType: 'pdf' | 'text';          // How the source was provided
  subtopic: string;                     // User-specified subtopic to teach
  fileName?: string;                    // Original PDF filename (if uploaded)
  characterCount: number;              // Length of source text (for validation)
}

// ============================================================
// ORACLE DATA — Generated by Oracle Agent
// ============================================================

interface OracleData {
  topicOutline: string[];               // Subtopic names only (sent to Tutee)
                                        // e.g. ["Light reactions", "Calvin cycle",
                                        //       "Chlorophyll", "ATP synthesis"]

  testQuestions: TestQuestion[];        // Questions for the Grader to administer
  answerKey: AnswerKeyEntry[];          // Expected answers for grading
  generatedAt: Date;                    // When Oracle finished processing
}

interface TestQuestion {
  id: string;                           // Unique question ID (e.g., "q1", "q2")
  question: string;                     // The question text
                                        // e.g., "What role does chlorophyll play
                                        //        in photosynthesis?"
}

interface AnswerKeyEntry {
  questionId: string;                   // References TestQuestion.id
  expectedAnswer: string;              // The correct answer from the source
                                        // e.g., "Chlorophyll is the pigment that
                                        //        absorbs light energy, primarily
                                        //        from the sun, to drive the
                                        //        light-dependent reactions."
  keyConcepts: string[];               // Core concepts that must be present
                                        // e.g., ["pigment", "absorbs light",
                                        //        "light-dependent reactions"]
  sourceExcerpt: string;               // Relevant excerpt from source material
                                        // (used for gap mapping in the report)
}

// ============================================================
// CONVERSATION DATA — Teaching session state
// ============================================================

interface ConversationData {
  messages: Message[];                  // Full conversation history
  coveredSubtopics: string[];          // Subtopics the user has addressed
                                        // Updated after each Tutee response
  tuteeState: TuteeState;             // Current visual state of the Tutee
  messageCount: number;                // Total messages exchanged
  startedAt: Date | null;              // When teaching started
  endedAt: Date | null;                // When user clicked "I'm Done"
}

interface Message {
  id: string;                           // Unique message ID
  role: 'user' | 'assistant';          // 'user' = teacher, 'assistant' = Tutee
  content: string;                     // Message text
  timestamp: Date;                     // When the message was sent
  tuteeState?: TuteeState;            // Tutee's state when this message was sent
                                        // (only for assistant messages)
}

type TuteeState = 'idle' | 'thinking' | 'confused' | 'test-taking';
// idle:         Resting, attentive — also used for "happy" moments via CSS bounce animation
// thinking:     Processing what the user just said, considering the explanation
// confused:     Didn't follow, about to ask a clarifying question
// test-taking:  Answering grader questions (S4), focused and concentrating

// ============================================================
// GRADING DATA — Test results and report
// ============================================================

interface GradingData {
  overallScore: number;                // Number of correct answers (e.g., 7)
  totalQuestions: number;              // Total questions administered (e.g., 10)
  percentage: number;                  // Score as percentage (e.g., 70)

  questionResults: QuestionResult[];   // Per-question breakdown

  tuteeTestAnswers: TuteeTestAnswer[]; // Raw Tutee answers (before grading)

  gradedAt: Date;                      // When grading completed
}

interface QuestionResult {
  questionId: string;                  // References TestQuestion.id
  question: string;                    // The question text (denormalized for display)
  tuteeAnswer: string;                 // What the Tutee answered
  expectedAnswer: string;             // What the correct answer was
  isCorrect: boolean;                 // Whether the Tutee got it right
  gap?: string;                        // If incorrect: what the user missed
                                        // e.g., "You didn't explain chlorophyll's
                                        //        role in absorbing light energy
                                        //        for the light-dependent reactions."
}

interface TuteeTestAnswer {
  questionId: string;                  // References TestQuestion.id
  answer: string;                      // Tutee's raw answer
  confidence: 'high' | 'low' | 'none'; // How confident the Tutee was
                                        // 'none' = "I don't know, this wasn't covered"
}
```

## Data Flow by Screen

| Screen | Client State Read | Client State Written | API Call |
|--------|------------------|---------------------|----------|
| **S1 — Upload** | — | `source.sourceText`, `source.sourceType`, `source.fileName` | — |
| **S2 — Topic** | `source.sourceText` | `source.subtopic`, `oracle.*` (all Oracle outputs from API response) | `POST /api/process-source` → returns `topicOutline`, `testQuestions`, `answerKey` |
| **S3 — Teaching** | `oracle.topicOutline`, `conversation.*` | `conversation.messages[]` (appended locally), `conversation.coveredSubtopics`, `conversation.tuteeState` | `POST /api/chat` → sends `message`, `conversationHistory`, `topicOutline`, `coveredSubtopics` |
| **S4 — Testing** | `oracle.testQuestions`, `oracle.answerKey`, `conversation.messages` | `grading.*` (from API response) | `POST /api/grade` → sends `conversationHistory`, `testQuestions`, `answerKey` |
| **S5 — Report** | `grading.*` (all grading data) | — (read-only display) | — |

## Session Lifecycle (Client-Side)

```
1. User lands on S1
   → AppState initialized: { currentScreen: 'upload', source: {}, oracle: null, ... }

2. User uploads source + enters subtopic (S1 → S2)
   → source.* populated locally
   → POST /api/process-source called
   → oracle.* populated from API response (topicOutline, testQuestions, answerKey)
   → currentScreen: 'teaching'

3. User teaches in chat (S3, multiple messages)
   → Each message: POST /api/chat with conversationHistory + topicOutline + coveredSubtopics
   → Client appends user message + tutee response to conversation.messages
   → conversation.coveredSubtopics updated from API response
   → conversation.tuteeState changes per response (idle → thinking → idle/confused)

4. User clicks "I'm Done Teaching" (S3 → S4)
   → conversation.endedAt set locally
   → currentScreen: 'testing'
   → POST /api/grade with conversationHistory, testQuestions, answerKey
   → Grader runs batched pipeline (2 LLM calls)

5. Grading completes (S4 → S5)
   → grading.* populated from API response
   → currentScreen: 'report'

6. User views report (S5)
   → Read-only. No more API calls.

7. User clicks "Start New Session" (S5 → S1)
   → AppState reset to initial values
   → Old state garbage-collected by React
```

## Client-Side Memory Considerations

- **Estimated state size:** ~50-100 KB per session (source text + conversation history + oracle outputs + grading results)
- **Request payload size:** Each `/api/chat` call sends conversationHistory (~0.5-2KB per message × up to 50 messages = ~25-100KB max). Acceptable for modern networks.
- **Conversation cap:** Limit to 50 messages per session to prevent unbounded state growth and large request payloads.
- **Browser refresh:** Refreshing the browser loses all state (React Context is ephemeral). Accepted for hackathon. V2: persist to `sessionStorage`.
- **No server-side memory concerns:** Backend is fully stateless — no session cleanup, no garbage collection, no cold-start data loss.

## V2 Migration Path

When adding persistence post-hackathon, the client-side types map directly to database tables:

| Client Type | Database Table | Notes |
|-------------|---------------|-------|
| `AppState` | `sessions` | Add `userId` foreign key, `sessionToken` for server-side answer key storage |
| `SourceData` | `sources` | Store file in S3/blob storage |
| `OracleData` | `oracle_outputs` | JSON column for outline/questions. Move `answerKey` to server-only storage. |
| `Message` | `messages` | Foreign key to session |
| `GradingData` | `grading_results` | JSON column for question results |

V2 additions:
- Add a `users` table for authentication and a `session_history` view for progress tracking.
- Persist `AppState` to `sessionStorage` for browser-refresh resilience.
- Move `answerKey` to server-side storage to prevent client-side cheating.
